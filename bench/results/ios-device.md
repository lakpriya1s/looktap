# iOS, real iPhone: every agent mobile tool, same steps, same app

Measured 2026-10-18 on Apple M3 Pro, macOS 26.5.2, a real iPhone 14 Pro (iOS 26.0) over USB. 10 runs per step per tool. Raw data: [`ios-device.json`](ios-device.json). Generated by `node bench/report.mjs ios-device`.

## How it was measured

- **App:** the system Settings app (`com.apple.Preferences`). No sign-in, nothing real is changed.
- **Tools:** looktap (looktap CLI), looktap-mcp (looktap 0.4.0), mobile-mcp (mobile-mcp 1.0.11), appium-mcp (MCP Appium 1.97.1), appium (Appium server (W3C HTTP)).
- **Driven like an agent:** MCP servers over stdio with `tools/call`; CLIs spawned once per command; raw Appium over W3C HTTP. When a tool cannot act on a label, the step reads the screen first and acts on what it found, and that read counts as a call.
- **Two times per step:** *answered in* is until the tool call returned; *reaction time* is until a neutral oracle saw the result on screen (the phone's screen as macOS gets it over the USB cable (the capture device QuickTime records from), read with Apple's Vision text recognition, ~0.1 s a read; it shares nothing with the tools: no XCTest runner, no WebDriverAgent, no accessibility query). A step passes only if the oracle saw it within 8 s.
- **Context:** bytes of every tool result, as an agent receives them. Screenshots are counted apart: some tools return the image inline, others a path to a file.
- **Neutral resets, not timed:** wherever a step needs a clean start (launch, swipe, scroll, fill, home, open URL, terminate), the app is force-stopped and relaunched at its first screen with plain `xcrun devicectl`, the same for every tool.
- **Fair start for every tool:** the iPhone is not rebooted (it would come back at its passcode). Instead every UI-test runner and helper the tools leave behind is stopped, on the Mac (`xcodebuild`, go-ios, Appium, MCP servers) and on the phone (looktap's runner, WebDriverAgent), and the run waits until the Mac is back at its idle CPU load. The phone stayed unlocked, charging over the USB cable, with Auto-Lock set to Never (set with looktap).
- **CPU and RAM:** `ps` every 250 ms over the tool's whole process tree, plus helpers it leaves outside it (WebDriverAgent, Maestro's driver, looktap's helper). The oracle's own commands are left out. Setup is measured separately. On the iPhone, the tools' runners (looktap's, WebDriverAgent) run on the phone, where they can't be measured: these are the Mac's numbers only.
- **Setup:** from starting the tool until its first screen read came back.

## Couldn't run on a real iPhone

- **ios-simulator-mcp**: drives simulators only (it takes a simulator UDID and runs idb underneath). Its error: `ui_describe_all: Input validation error: Invalid arguments for tool ui_describe_all: udid: Invalid string: must match pattern /^[0-9A-Fa-f]{8}-[0-9A-Fa-f]{4}-[0-9A-Fa-f]{4}-[0-9A-Fa-f]{4}-[0-9A-Fa-f]{`
- **mobilebuildmcp**: its UI automation works on simulators only. Its error: `snapshot_ui: Error Parameter validation failed: Invalid parameters: simulatorId: Invalid Simulator UUID format ├ Category: validation Code: PARAMETER_VALIDATION_FAILED`
- **maestro-mcp**: doesn't list a real iPhone. Maestro's real-iPhone driver (`maestro driver-setup --apple-team-id`) uses bundle IDs registered to Maestro's own team (`dev.mobile.maestro-driver-ios`), so no other team can sign it. Its error: `inspect_screen: Failed to inspect screen: Device with id <device> is not connected`
- **idb**: its UI commands (`idb ui …`) work on simulators only. Its error: `Command failed: idb ui describe-all --json --udid <device> Target is not a simulator, cannot provide accessibility commands: <device> | <device name> | Booted | iPhone 14 Pro | OS 'iOS 26.0'`

## Notes

- **n/a** means the tool has no way to do the step. Every tool that ran on the iPhone could do every step.
- **looktap MCP actions return the settled screen** by default (`ls: false` turns it off): one call does the action, waits for the animation to finish and reads the next screen, which the other tools need a second call for. That wait is in its times.
- **Reaction time is what was drawn:** the oracle reads the screen's pixels, so a result counts once it shows, animations included (on the simulator it is the accessibility tree, which can change before an animation has finished drawing).
- **Written by looktap's author.** The scenario and every adapter are mine, and looktap was developed on this app. The adapters are in `bench/adapters-ios.mjs` and `android.mjs`; corrections from the other tools' authors are welcome.
- **Failures were not re-run.** A step was re-run only when the benchmark itself was at fault (listed below), never because a tool failed.
- The Mac was not otherwise idle (other apps running); every tool waited for the same idle level before it started, and the level at its start is listed below.
- **looktap 0.4.0**, the installed npm release (`@looktap/cli`). Its `home` and `stop` commands (since 0.3.0) are used for home and terminate; the simulator results are from 0.2.1, which had neither.
- **The iPhone's Settings** differ from the simulator's: account and offer banners at the top push General below the fold, so the tapped row is “Family” (the first row with a plain label), checked by its page's “Subscriptions” heading. No text from the screen is stored in the results, only sizes and times. The scroll target is “Developer”; iOS 26's floating search bar covers the bottom of the list, so a row under it counts as off screen (for the oracle, which can't read it, and for the adapters' scroll loops).
- **Links open in the default browser**, which on this iPhone is Brave: a tool that opens a URL through the system lands there, while Appium's `deepLink` names Safari. The oracle accepts example.com's page in any browser, and the reset closes them all.
- **WebDriverAgent** (Appium's, version 16.15.0) was built once beforehand and signed with the owner's personal team; Appium MCP, raw Appium and mobile-mcp all used that build. Raw Appium ran from the same Appium install appium-mcp uses (Appium 3.5.2, xcuitest 12.1.0) with the session settings appium-mcp sets for iOS (`animationCoolOffTimeout` 0.5 s, `maxTypingFrequency` 45, `pageSourceExcludedAttributes`), so only the MCP layer differs. With the defaults, raw Appium took ~7 s an action on the phone, waiting for Settings' banners to stop animating.
- **mobile-mcp on a real iPhone** goes the way its wiki gives: go-ios's tunnel (userspace), WebDriverAgent started with go-ios, port 8100 forwarded, `MOBILEMCP_LEGACY_ROBOT=1`. Its default agent (mobilecli's) needs a wildcard App ID, which a free personal team can't have. Starting go-ios and WebDriverAgent counts in its setup. On a real iPhone its element list has no refs, so taps go to the element's centre.
- **Raw Appium, scroll to label:** on the phone `mobile: scroll` returns after a page or so with the element still off screen, so raw Appium calls it again until the element's frame is on screen (each look and scroll is a call). Appium MCP's `scroll_to_element` worked as is.
- **Fill:** the oracle accepts the typed text anywhere on screen (“Wi-Fi” in the results doesn't count).
- **Status bar:** the capture device shows a clean status bar (9:41), so the oracle never reads the clock.
- **The two failures:** in one run Appium MCP's swipe left Settings in search mode (the search field open, a “T” typed) instead of scrolling the list; in one run raw Appium's `mobile: terminateApp` answered, but Settings was still running 8 s later. Both count as failures.

Re-run after a fix to the benchmark (not to the tool):

- **maestro-mcp**, setup: setup re-checked: the runner had stored the notice Maestro's reply opens with instead of its error (re-run 2026-10-18)

Shared daemons (`idb_companion`, the adb server), used by several tools and by the oracle, are not counted in any tool's RAM: up to 23 MB.

Idle Mac before the runs: 19% CPU busy, 4401 MB reclaimable. Busy % when each tool started: looktap 13%, looktap-mcp 11%, mobile-mcp 12%, appium-mcp 12%, appium 24%.
