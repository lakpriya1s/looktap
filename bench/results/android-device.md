# Android, real phone: every agent mobile tool, same steps, same app

Measured 2026-10-17 on Apple M3 Pro, macOS 26.5.2, a real Samsung Galaxy A06 (SM-A065F, Android 16, One UI, 720×1600 at 300 dpi) over USB. 10 runs per step per tool. Raw data: [`android-device.json`](android-device.json). Generated by `node bench/report.mjs android-device`.

## How it was measured

- **App:** the system Settings app (`com.android.settings`). No sign-in, nothing real is changed.
- **Tools:** looktap (looktap CLI), looktap-mcp (looktap 0.4.0), mobile-mcp (mobile-mcp 1.0.11), maestro-mcp (maestro 1.0.0), appium-mcp (MCP Appium 1.97.1), appium (Appium server (W3C HTTP)), adb (adb + uiautomator).
- **Driven like an agent:** MCP servers over stdio with `tools/call`; CLIs spawned once per command; raw Appium over W3C HTTP. When a tool cannot act on a label, the step reads the screen first and acts on what it found, and that read counts as a call.
- **Two times per step:** *answered in* is until the tool call returned; *reaction time* is until a neutral oracle saw the result on screen (`dumpsys`: the resumed activity, the fragments on screen and the view tree. It shows no text, so text steps are checked by what they change: the search screen's results list fills, the list moves). A step passes only if the oracle saw it within 8 s.
- **Context:** bytes of every tool result, as an agent receives them. Screenshots are counted apart: some tools return the image inline, others a path to a file.
- **Neutral resets, not timed:** wherever a step needs a clean start (launch, swipe, scroll, fill, home, open URL, terminate), the app is force-stopped and relaunched at its first screen with plain `simctl`/`adb`, the same for every tool.
- **Fair start for every tool:** the phone is not rebooted (it would come back at its PIN screen). Instead every tool's on-device helpers are stopped (looktap's and mobile-mcp's servers, `uiautomator`, Appium's and Maestro's apps), so none holds the phone's one UiAutomation connection, whatever the previous tool left running on the Mac is killed, and the run waits until the Mac is back at its idle CPU load. The phone stayed unlocked, charging over the USB cable, with Stay awake on.
- **On the device:** Android tools keep helpers inside the phone (Appium's UiAutomator2 server, Maestro's driver, looktap's helper) or run one-shot `uiautomator`, `input` and `screencap` commands there. The device's own `ps`, sampled every second, measures those; the Mac-side numbers can't see them.
- **CPU and RAM:** `ps` every 250 ms over the tool's whole process tree, plus helpers it leaves outside it (WebDriverAgent, Maestro's driver, looktap's helper). The oracle's own commands are left out. Setup is measured separately.
- **Setup:** from starting the tool until its first screen read came back.

## Notes

- **n/a** means the tool has no way to do the step. Every tool could do every step on the phone (looktap 0.4.0 has `stop`).
- **looktap MCP actions return the settled screen** by default (`ls: false` turns it off): one call does the action, waits for the animation to finish and reads the next screen, which the other tools need a second call for. That wait is in its times.
- **Reaction time measures the UI state** the oracle reads (accessibility tree, activity and fragments), which can change before an animation has finished drawing.
- **Written by looktap's author.** The scenario and every adapter are mine, and looktap was developed on this app. The adapters are in `bench/adapters-ios.mjs` and `android.mjs`; corrections from the other tools' authors are welcome.
- **Failures were not re-run.** A step was re-run only when the benchmark itself was at fault (listed below), never because a tool failed.
- The Mac was not otherwise idle (other apps running); every tool waited for the same idle level before it started, and the level at its start is listed below.
- **`uiautomator dump`** (how mobile-mcp and raw adb read the screen) waits for the UI to go idle first, so a read right after an animation takes ~5 s on Android 16.
- **On-device numbers** come from sampling the device's `ps` once a second, so one-shot commands shorter than that can be missed. For mobile-mcp none were caught: its on-device cost is unknown, not zero.
- **Raw Appium** ran from the same Appium install appium-mcp uses (Appium 3.5.2, UiAutomator2 driver 8.1.0), so only the MCP layer differs.
- **Samsung's Settings** differ from the emulator's: the tapped row is “Connections”, the scroll target “About phone”, search is a “Search settings” button (a content description, no text) opening `com.android.settings.intelligence`, its field an `AutoCompleteTextView`, and links open in Samsung Internet. Each tool used its own way to find them: Appium and adb by description and class, the others by label.
- **Fill opens a second screen:** tapping “Search settings” starts the search activity, then the text goes into its field. Between those two calls the runner waits 2 s, not counted, for the model's turn. Maestro does both in one call and waits by itself.
- **Raw Appium, scroll to label:** Appium's `UiScrollable` stopped halfway down One UI's list (nested in a scrolling header), so raw Appium looked for “About phone” and swiped until it was there, as an agent over HTTP would (each look and swipe is a call). Appium MCP's `scroll_to_element` worked as is.
- **Scroll to label** (to “About phone”) is checked by the list having moved: `dumpsys` shows no text, so whether the row is fully on screen relies on the tool.
- **The phone's load** idles near 27 (One UI's own background work), so unlike the emulator, runs didn't wait for it to drop; the load at each run's start is in the raw data.
- **Terminate:** on the phone, Appium's `mobile: terminateApp` did stop Settings (on the emulator it answered success but left it running).

Re-run after a fix to the benchmark (not to the tool):

- **looktap**, terminate app: looktap 0.4.0 has `stop`; the adapter still marked terminate n/a (re-run 2026-10-18)
- **looktap-mcp**, terminate app: looktap 0.4.0 has `stop`; the adapter still marked terminate n/a (re-run 2026-10-18)

Shared daemons (`idb_companion`, the adb server), used by several tools and by the oracle, are not counted in any tool's RAM: up to 37 MB.

Idle Mac before the runs: 9% CPU busy, 4927 MB reclaimable. Busy % when each tool started: looktap 9%, looktap-mcp 8%, mobile-mcp 5%, maestro-mcp 10%, appium-mcp 6%, appium 7%, adb 6%.
